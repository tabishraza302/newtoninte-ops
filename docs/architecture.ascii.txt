3. CONCURRENCY: TWO USERS CLAIM THE SAME ITEM
---------------------------------------------

   User A -----\
                \                                    +---------------------------+
                 +-->  POST /items/42/claim  -------> |  UPDATE work_items        |
                /                                    |    SET assignee_id = A,   |
   User B -----/                                     |       status='in_progress'|
                                                     |        version = version+1|
                                                     |  WHERE id = 42            |
                                                     |    AND team_id = ?        |
                                                     |    AND status='open'      |
                                                     |    AND assignee_id IS NULL|
                                                     +-------------+-------------+
                                                                   |
                              +------------------------------------+----------------------------+
                              |                                                                 |
                      1 row affected                                                  0 rows affected
                              |                                                                 |
                              v                                                                 v
                    200 OK   (A owns it)                                            409 ALREADY_CLAIMED

   No read-then-write window. The DATABASE picks the winner.

4. ASYNC PATH: TRANSACTIONAL OUTBOX
-----------------------------------

   REQUEST (synchronous)                                    BACKGROUND (worker)

   service txn
   +----------------------------+
   | UPDATE work_items          |
   | INSERT activity_event      |
   | INSERT outbox_jobs --------+-----------------+
   |      (same COMMIT)         |                 |
   +----------------------------+                 |
                                                  |
   respond 201 immediately                        |
   (email NOT sent yet)                           |
                                                  v
                                     +---------------------------+
                                     |  WORKER poll loop         |
                                     |                           |
                                     |  SELECT * FROM outbox_jobs|
                                     |   WHERE status='pending'  |
                                     |     AND available_at<=now |
                                     |   ORDER BY id LIMIT 10    |
                                     |   FOR UPDATE SKIP LOCKED  |
                                     +-------------+-------------+
                                                   |
                                     +-------------v-------------+
                                     |  mark 'processing'        |
                                     |  send via SMTP (Nodemailer)|
                                     +-------------+-------------+
                                                   |
                              +--------------------+--------------------+
                              |                                         |
                           success                                   failure
                              |                                         |
                              v                                         v
                      status='done'                    attempts++ ;
                                                       available_at = NOW() + backoff
                                                       last_error = ...
                                                       attempts >= max -> status='failed'
                                                       (visible, never silently dropped)

   Enqueue is atomic with the change. Delivery is AT-LEAST-ONCE;
   dedupe_key makes the handler effectively once.

5. AUTH: REFRESH ROTATION WITH REUSE DETECTION
----------------------------------------------

   Browser                 API                            MySQL
      |                     |                               |
      | POST /auth/refresh->|                               |
      |   (cookie RT1)      | BEGIN                         |
      |                     | SELECT ... FOR UPDATE ------->|
      |                     |  (row for hash of RT1)        |
      |                     |<------------------------------|
      |                     |                               |
      |              +------+--------+                      |
      |              |  RT1 state?   |                      |
      |              +------+--------+                      |
      |                     |                               |
      |       current ------+------- revoked                |
      |          |                          |               |
      |          v                          v               |
      |    new RT2, revoke RT1        replaced < grace ago? |
      |    COMMIT                           |               |
      |          |                   +------+------+        |
      |          |                  yes            no       |
      |          |                   |              |       |
      |          v                   v              v       |
      |   200 + Set-Cookie RT2   200 (new RT)   revoke ENTIRE family
      |                                         401 UNAUTHENTICATED (theft)

   Only hashes are stored, so the benign-race path MINTS a new successor in the
   family (revoking the prior one); a successor is never read back from the DB.

6. DATA MODEL
-------------

   Relationships (every foreign key is shown here):

     users ----< memberships >---- teams
     users ----< membership_events >---- teams        (actor_id, subject_user_id)
     users ----< invitations ;  teams ----< invitations      (created_by)
     users ----< refresh_tokens
     users ----< password_reset_tokens
     users ----< idempotency_keys
     teams ----< work_items ;   users ----< work_items       (created_by, assignee_id)
     work_items ----< activity_events ;  users ----< activity_events   (actor_id, null = system)
     work_items ----< comments ;         users ----< comments          (author_id)
     outbox_jobs                                            (standalone: no FK by design)

   Every table has created_at; mutable tables also have updated_at. Append-only tables
   (activity_events, membership_events, comments) have neither updated_at nor any
   update/delete path.

7. WORK ITEM LIFECYCLE
----------------------

   open --claim/start--> in_progress --submit--> awaiting_approval
    |    (member) or start     ^                        |
    |     (assignee)           |                        | approve (LEAD ONLY)
    |                          | send back (lead)       v
    |                          +------------------  resolved
    |                                                  |  |
    |                                       close(lead)|  | reopen(lead)
    |                                                  v  +--> in_progress
    |                                              closed  [end]
    |
    +-- cancel (creator or lead) --> cancelled  [end]

   cancel is also allowed from in_progress and awaiting_approval
   (by the creator or a lead). It is NOT allowed from resolved.

   An item is NEVER in_progress without an assignee.
   Every arrow writes an activity_event in the SAME transaction as the status change.

8. SYNC vs ASYNC BOUNDARY
-------------------------

   SYNCHRONOUS (in the request)          ASYNCHRONOUS (outbox -> worker)
   ------------------------------        ------------------------------------
   create / edit / claim / transition    email.reset
   authorization decision                email.invite
   activity event write                  email.assigned
   idempotency key + stored response
   outbox row insert

   If it must be consistent with the item -> synchronous.
   If it is a side effect that can fail and retry -> a job.
